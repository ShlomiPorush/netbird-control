# MSP Tenants

Manage customer accounts (tenants) under a NetBird Cloud **MSP** account, and manage each customer's network - from inside the app.

*Where:* **Tenants** (sidebar, admins only). *Appears only when* the connected NetBird account is an **activated MSP parent** - detected via `GET /api/integrations/msp` (non-MSP accounts simply never see the feature).

## Managing tenants

The Tenants page mirrors the official dashboard's MSP portal:

- **Add Tenant** - name + the customer's email domain + **Permission Groups**: groups of *your* account whose members may access the tenant, each with a role (Admin / Network Admin / User).
- **Initial Setup** (create only) - the General tab carries an **Initial Setup** group of four optional steps that run automatically right after the tenant is created, each best-effort and re-runnable later: **Sync Settings From Defaults** (checked - seeds from the Tenant Defaults profile, see below), **Create Managed Service User** (checked - provisions the service user + token, see below), **Configure Account Notifications In NetBird** (checked - points NetBird's account notifications at the tenant's `/t/<id>` receiver), and **Configure Activity Events In NetBird** (unchecked - **requires a NetBird Business plan** for event streaming). Provisioning runs before seeding (the settings copy authenticates as the tenant), and the two webhook steps run after creation with the tenant's own credentials (falling back to the main-token account switch when provisioning was skipped/failed). The response + `tenant.create` audit carry a compact `setup` summary (per step: skipped, or attempted true/false); if any *requested* step fails you get a non-blocking **Tenant Created - Setup Incomplete** notice listing what to re-run (Apply Defaults, the key icon to Provision, the Settings - Webhook buttons). Leaving all four at their defaults replicates the previous always-on behavior plus the notifications step.
- **Default seeding** - on creation, the app seeds the new tenant from the **Tenant Defaults profile** so it starts consistent, not blank: event-filter rules + built-in-noise toggle, the global blocklist entries (network-scoped `only`/`except` ones are skipped), a data-retention window, and the **full official NetBird account settings set** (peer approval, user-approval-required, multi-factor authentication with its remember-browser option, peer session expiration, require-login-after-disconnect, groups propagation, JWT group sync with claim + allow-groups, restrict-regular-users, routing-peer DNS, traffic events with kernel traffic reporting, automatic updates, peer expose, lazy connections, and optionally the DNS domain / network ranges). Only account-specific group-based settings (peer-expose-groups, IPv6-enabled-groups) are excluded, as their group ids are not portable across accounts - with one deliberate exception: the profile's **Disable IPv6** toggle clears a tenant's IPv6 Enabled Groups (an empty list is the official disable mechanism), which needs no group ids; left off, tenant IPv6 is never touched. The infra fields (DNS domain, network range, IPv6 network range) are written to a tenant **only when the profile explicitly sets them** - left blank they are never touched, so a tenant keeps its own addressing. Peer inactivity is fixed at 10 minutes, exactly like the official dashboard. The profile is an **explicit admin-defined reference** (Settings → Tenant Defaults, MSP only) rather than a live copy of main - "not everything right for us fits our customers"; each nb toggle, the retention window and the two copy flags (filter rules / blocklist) are curated per field, and the nb group can be turned off entirely. If no profile has been saved the seeding falls back to copying **main's current live config** (the original behavior, unchanged), and the copy flags gate the filter-rules and blocklist copies (when off, the tenant's own rows are left untouched). The NetBird-settings write happens *after* the tenant's managed service user is provisioned (the create flow provisions first, then seeds), since that write authenticates as the tenant; if provisioning failed it still tries via the main-token account-switch fallback. Seeding is best-effort and per-step - a failure never blocks tenant creation (the manual **Apply Defaults** action below re-runs it), the NetBird-settings step can fail on its own without losing the app-config copy (reported as `nbSettings` in the summary, alongside `copiedRules`/`copiedBlocklist` flags). Cloud MFA is applied as its own best-effort step against the per-account MFA service (`POST /api/service/mfa`, not part of the settings blob), reported separately as `mfa` in the summary so it can fail without breaking the rest. Note: not every NetBird API base serves that MFA route (the public management API answers it with a plain-text 404) - the app probes once (1h cache) and, when unavailable, skips the step, omits the drift row, and disables the MFA controls in Tenant Defaults with an explanatory note. The copied summary is recorded in the `tenant.create` audit.
- **Plan** (edit modal → **Plan** tab, active tenants only, admin + main account only) - the official MSP plan tab replicated: the **Team** and **Business** cards side by side with each plan's description, its price **per user / month** in your MSP account's own billing currency, the shared limits (Unlimited Users, 100 machines + 10 per user) and the plan's feature checklist, all read live from NetBird's plan catalog (`GET /api/msp/billing-plans`, cached ~10 minutes). The tenant's current tier shows a disabled **Current Plan** button; the other card offers **Upgrade To …**. **This is a real billing action** - the plan is charged to your MSP account - so the click goes through an explicit confirmation naming the tenant, the plan and the price, and the change is audited as `tenant.plan`. Under the hood the app mirrors the official flow exactly: a tenant on **free or trial** gets a `POST` to `/api/integrations/msp/tenants/<id>/subscription`, an already-paying tenant a `PUT` to the same path, with the price id of the plan in the active currency. The tenant's tier is read in the tenant's own context first (so the verb is never chosen from main's subscription), the price id is validated against the catalog before any call, the endpoints refuse to run in tenant context, and `NETBIRD_READONLY` blocks them entirely. NetBird's own error text is surfaced inline on failure.
- **Domain verification** - a new tenant is *Pending Verification* until you publish a TXT record on the customer domain: host = the domain, value = `nb-verification=<challenge>` (shown with copy buttons). **Check Again** re-validates; records can take a few minutes to propagate.
- Per-tenant **Users / Peers** counts (from NetBird's billing usage), status badges, edit (name + permission groups), and delete.
- **Apply Defaults / drift** (per tenant, main account only) - re-seed one tenant from the **Tenant Defaults profile** on demand (**replace** semantics, same as creation, including the NetBird account settings), or view a **drift** report (the **Settings Sync** modal) that compares the tenant's config against the **profile** content-wise. The `Default` column carries the profile's value (or main's live list for filter rules / blocklist, which are the copy source). Rows are **gated by the profile's flags**: filter rules + built-in noise appear only when the filter-rules copy flag is on, blocklist entries only when the blocklist copy flag is on, and the **NetBird account settings** rows only when the profile's nb group is enabled - **one granular row per setting** (labelled `NetBird: …` so they group visually - Peer Approval, User Approval Required, Multi-Factor Authentication, Peer Session Expiration, Require Login After Disconnect, Groups Propagation, JWT Group Sync, Restrict Regular Users, DNS Domain / Network Range / IPv6 Network Range (only when the profile sets them), IPv6 (only when Disable IPv6 is on), Routing Peer DNS Resolution, Traffic Events, Traffic Reporting (Kernel), Automatic Updates, Peer Expose, Lazy Connections). Retention always compares against the profile value. The report also shows whether the tenant's activity + notifications webhook tokens are configured. Webhook tokens are shown for reference and are never overwritten by Apply.
- **Tenant Defaults** (Settings → Tenant Defaults, MSP only) - the single admin-edited profile the seeding, Apply Defaults and drift all read. It holds the flat NetBird account-settings map covering the **full official settings set** (each toggle, with an on/off master for the whole nb group), the retention window (days, or blank = keep forever), and the two copy flags (filter rules / blocklist). Group-based settings are excluded (not portable), the infra fields (DNS domain / network ranges) are applied only when explicitly filled in, and peer inactivity is fixed at 10 minutes like the official dashboard. A **Load Current Main Values** action fills the form from main's live config as a starting point (never the infra fields). Until a profile is saved, everything falls back to copying main.
- **NetBird Settings** (Settings → NetBird Settings, admin) - the **live editor for the current account's own NetBird settings**, distinct from Tenant Defaults: this reads and writes the account's **actual** settings object rather than a stored template. It works for **main and for a managed tenant** (Settings runs in tenant context too, and the backend read/write is ALS-aware - in tenant mode it edits *that tenant's* account). It renders the same field set as Tenant Defaults (Authentication, Groups, Permissions, Networks, Clients - the components are shared, not duplicated) but with **no master toggle, no copy flags and no retention section** (retention has its own tab). A single **Save Settings** button writes the whole account: the app builds the settings patch with the same builder seeding uses, **merges** it onto the account's current settings (never a bare replace - fields the patch doesn't set are preserved), and `PUT`s `/api/accounts/<id>`. The **infra fields** (DNS domain, network range, IPv6 network range) are editable here but carry a prominent **re-allocation warning** - changing them re-allocates every peer's IP - and are sent **only when actually changed** from the current value, so a no-op save never triggers a re-allocation. The seeding-only *Disable IPv6* convenience is intentionally omitted (a live account's IPv6 is managed by its IPv6-enabled-groups, not a blanket clear). **Cloud MFA** (enable + remember-browser) is applied as its own best-effort step against the per-account `/api/service/mfa` service; when the NetBird API base doesn't serve that route the MFA controls are disabled with an explanatory note. Saving is audited as `settings.netbird_account` (auto-tagged with the tenant id in tenant mode). `NETBIRD_READONLY` blocks the write.
- **Readiness chip** - each tenant row shows an onboarding checklist as an `N/5` chip covering five prerequisites: **domain verified** (status active), **service user** (a managed or manual tenant API token is stored), **events webhook** (the tenant's activity ingest token is set), **notifications webhook** (its account-notifications token is set), and **Telegram** (the tenant's own Telegram config exists and is enabled). It is computed cheaply from settings + the tenant row alone - no per-tenant NetBird calls - so listing tenants stays fast (one batched settings read covers every tenant).
- **Fleet Report** (a tab on the Tenants page, main account only) - a one-screen management snapshot with one row per non-invited tenant. Most metrics come from the app's own database + settings; the **management figures** (plan, users, billed users, known issues) are fetched per tenant **in the tenant's own context** (its own PAT, same guard as the tenants table's usage fetch - a tenant with no working context simply shows those cells as `-`), which is why the report is **on-demand** with a manual refresh. Columns: **Plan** (tier + trial suffix, from the tenant's `billing/subscription`, same mapping as the tenants-table Plan cell), **Users** active / total and **Billed** users (from the tenant's `billing/usage`, billed users falling back to the tenant's latest billing admin-event), peers **total / online / offline 30d+**, **outdated clients** (versions behind the highest client version seen across all accounts, compared by major.minor so a patch-level lag never flags), **known issues** (this now equals exactly what the tenant's **Known Issues banner** shows - `getNbNotices` run in the tenant's context, so the 48h routing window, newest-per-peer/message dedup and connected-router self-resolve all apply, instead of a raw undismissed-count that over-reported stale/duplicate/resolved items), the webhook / Telegram / service-user readiness flags (service-user also flips off when its token has expired), and the **last event** timestamp (newest of the tenant's activity + admin events). Every column is sortable.
- **Weekly Digest** (Fleet Report → Digest, main account only) - an optional recurring summary of the whole fleet. **Disabled by default** (a production kill switch); when enabled you pick a **day** (0-6) and **hour** (0-23, in the app time zone) and choose the channels: **main's Telegram** and/or a list of **emails**. The scheduled send self-gates to once per day. A **Send Now** button sends immediately without enabling the schedule (it still stamps the daily marker, so that day's scheduled run won't duplicate it). It opens with **fleet totals** (tenants, active users, billed users, peers, known issues), then each tenant gets a compact block - plan (tier + trial), users active/total, billed users, peers total (online), offline 30d+, outdated clients, known issues and any missing-readiness marks - over Telegram (HTML) and email (a table with the same columns + a totals line). Saving the config is audited as `settings.msp-digest`; a manual send as `msp-digest.send`. A failing scheduled run raises the standard background-job alert (System Health → *mspDigest*).
- All actions are audited (`tenant.create/update/delete/verify`, `tenant.defaults`, `settings.tenant-defaults`, `settings.netbird_account`, `settings.msp-digest`, `msp-digest.send`).

## Managing a customer's network (tenant mode)

Click **Manage** on an active tenant. Technically this mirrors the official dashboard: every management API call carries the same token plus `account=<tenantId>` - no re-authentication.

- The top bar turns orange with a **"Managing Tenant: X"** chip (no extra banner, no lost screen space); its **X** exits back to your account.
- **Tenant mode is per browser tab.** The browser keeps only the managed tenant's id, in the tab's session storage; the name shown in the chip comes from the tenant list. So:
  - Reloading the page, or signing out and back in, in the same tab keeps the tenant.
  - Two tabs can manage different tenants at the same time; switching in one tab never changes another.
  - A new, empty tab starts in your main account. In Chromium-based browsers this also applies to a tab opened from a link in the app (for example, with a middle-click). Typing a URL into a tab that already manages a tenant keeps that tenant.
  - Some browsers copy session storage into a tab opened from a link or with **Duplicate Tab**, so that tab starts in the same tenant. After it opens, it is independent.
  - If the tenant was removed or can no longer be managed, the tab returns to your main account.
- **The rule: a tenant behaves exactly like the main account - same mechanism per feature.** The main account is simply tenant `''` internally.
  - Pages that are API-direct for main (Networks, Policies, Groups, Posture, Access Profiles, Blocklist, Cleanup, Reverse Proxy services) are API-direct for the tenant too - read and write, fully isolated.
  - Data that main SYNCS into the database is synced per tenant the same way: the **peers/users mirrors** refresh for every account on the same schedule, and **Peers / Users / IP History / Dashboard / Activity / Admin** read tenant-scoped stored rows with the exact same pages - nothing is fetched "live on page view".
  - **Event ingestion** is webhook-driven for every account: while managing a tenant, open **Settings → Webhook** to set that tenant's own Bearer token(s) and copy its endpoint URL - which carries the tenant id (`/api/webhook/t/<tenant-id>`, and `/api/integrations/netbird-notifications/t/<tenant-id>` for account notifications) - then configure it in that tenant's NetBird event-streaming / notifications integration. The id in the URL routes the tenant's activity + traffic events straight into its own rows, exactly like the main account's. Until configured, its history pages are simply empty - like a fresh install.
  - **One-click NetBird notifications setup** - **Settings → Webhook** also offers a one-click action that configures the account's NetBird **Account Notifications** webhook channel automatically (works for main and for a managed tenant). It mints a fresh notifications ingest token, stores it, and creates or updates the account's single webhook channel to point at our `/api/integrations/netbird-notifications` receiver (or `/t/<tenant-id>` in tenant mode) with **all** event types. Because a stored token's plaintext can't be recovered, the token is always rotated on setup (surfaced as `rotatedToken` in the response); audited as `webhook.nbsetup`.
  - **One-click NetBird Event Streaming setup** - the same page also configures the account's **Event Streaming** (the Generic HTTP integration) automatically per account: it creates or updates the `generic_http` integration to point at that account's `/api/webhook` receiver (`/t/<tenant-id>` in tenant mode) with an `Authorization: Bearer` header. The events ingest token is rotated for a tenant (or for main without an env token); when the main account's token is env-managed (`WEBHOOK_AUTH_TOKEN`) it is reused as-is and **not** rotated (`rotatedToken:false`). Audited as `webhook.nbstream`. **Requires the NetBird plan that includes event streaming** - a tenant whose plan lacks it gets NetBird's own error surfaced verbatim (as a 502).
- **Reverse Proxy access logs** sync per account too - each tenant's Cloud ingress logs land in its own scoped rows, same page, same retention.
- **App features run per tenant as well**: Temporary Access (grants + expiry/reconcile jobs), Recurring Access, Recertification (per-account rounds and daily gate) and Automations - each background job iterates every account in its own context, a failing tenant never blocks the others. **Notifications** go to the acting account's own Telegram (see below); access-review scheduler alerts additionally **mirror to main** with the tenant's name, under the Tenant Activity toggle.
- **Event Filtering** is per tenant: each account keeps its OWN filter rules + built-in-noise toggle, and its webhook traffic is filtered by those rules at ingest. The gated purge tool (matching preview + delete) acts on that account's stored events only.
- **System Health** is available while managing a tenant: the account-scoped numbers (event / admin-event / audit / IP-history row counts and oldest rows, active grants, scheduled bypasses, bypassed peers, retention window, NetBird API health via the tenant's own token) reflect the tenant. Total DB size and the global infra fields (version, node, uptime, scheduler list, notification queues) are shared and shown as-is.
- **Dashboard** is per tenant: the **billed-users** tile and the **Known Issues** notices (routing-peer / integration alerts from the tenant's own `/t/<id>` notifications receiver, admin-dismissable per account) both show the tenant's own data, not main's.
- **Apply to All Tenants** (main account only): from **Event Filtering** and **Blocklist**, an admin can push main's configuration to every tenant at once - **replace** semantics (each tenant's own rules/entries are overwritten). Blocklist propagation skips network-scoped entries (`only`/`except`), since those reference main-account network ids that don't exist under a tenant. These endpoints refuse to run in tenant context. New tenants get this config automatically (default seeding on creation); the per-tenant **Apply Defaults** and **drift** view (on the Tenants page) do the same for one tenant on demand and show where a tenant has diverged from main.
- **Still main-account-only** (by design): access requests / self-service Request Access (requesters are your SSO users), the pending-request badges (sidebar + dashboard tiles), the outbound notifications log (**Admin → Notifications**, an app-level record), the weekly digest, anomaly alerts, and most app settings. These no longer fire their queries in tenant mode - the UI hides them there, so the console stays quiet rather than logging 403s. The Settings exceptions, which ARE per-tenant, are **Settings → NetBird Settings** (the tenant's own live NetBird account settings - the live editor edits whichever account is active), **Settings → Webhook** (the tenant's own ingestion tokens + `/t/<id>` endpoints), **Settings → Data Retention** (the tenant's own purge window) and **Settings → Telegram** (the tenant's own bot/chat/topics + event selections, stored under `telegram_config:<tenant>` / `telegram_bot_token:<tenant>`, settings-only - never env) - in tenant mode Settings shows only those sections. The Telegram **Tenant Activity** toggle (mirror tenant audit + access-review alerts into main's channel, default on) is **main-only** - it is never shown or writable in tenant mode. The server route allowlist refuses everything else in tenant mode with 403.
- Audit entries made in tenant mode carry a `tenant` field, so you always know which account a change touched.

## Support users

Tenant management no longer requires being a main-account admin. Grant the **Tenant Support** feature permission (Settings - Permissions) to a non-admin user or group and they become a delegated MSP operator.

- **What it allows**: switch into any linked tenant from the switcher, and manage that tenant *exactly like an admin while inside it* - every in-context page and action (Peers, Networks, Policies, Blocklist, Event Filtering, Reverse Proxy, Temporary Access, System Health, ...), plus the full **Troubleshoot** page for the tenant's own devices.
- **What it does NOT allow**: any admin power on the **main** account (they stay a restricted user there - only their own data and whatever other feature permissions they hold), and **creating, editing or deleting tenants** or their credentials. Only the three read-only MSP endpoints the switcher needs (status, tenants list, switcher) are open to them; every create/update/delete/token/provision endpoint stays strictly admin-only.
- **How it works**: the elevation is scoped to a single validated request. When a support user's request carries the tenant header AND targets an in-context route, the server treats them as admin *for that request only*; a request without the header, or one aimed at a main-only or MSP-admin route, is never elevated. Audit rows always record the real (non-admin) user, never a synthetic admin.

## Managed service users (tenant API access)

The main API token belongs to a **service user**, and NetBird's permission groups cannot contain service users - so it cannot switch into tenants (the app detects a silently ignored switch and fails loudly rather than ever showing main-account data under a tenant banner). Instead, **the app manages tenant credentials itself**:

1. **One-time setup**: in Settings → NetBird API, save the **MSP Provisioning Token** - a token of a *real user* (an MSP admin who is in the tenants' permission groups). It is used ONLY for provisioning and for **user invitations** (NetBird Cloud rejects an invite issued by a service user - "inviter user ... is empty" - so the invite/resend call is made as this real user, in the main account and in tenants alike), never for routine calls.
2. **Per tenant** (automatic on tenant creation, or the key icon → **Provision Automatically**): the app creates a **service user named like the app** inside the tenant, issues it a 365-day access token, deletes older tokens, and stores the new one (write-only, backup-excluded). All management calls for that tenant then use its own token.
3. **Rotation**: an hourly background job re-issues any tenant token within 30 days of expiry (visible in System Health as *Tenant Token Rotation*; failures raise the standard job alert). The key icon turns **amber** when a token is close to expiry - i.e. rotation is failing.
4. **Visibility**: the key icon on each tenant row opens *Tenant API Access* - the managed service user's name, last rotation and token expiry, plus **Rotate Now**.

A manual token paste remains available as an advanced fallback (not auto-rotated). Without any tenant token, the app falls back to main-token account switching, verified once per 10 minutes.

## Gotchas

- The API token must belong to the MSP **parent** account. If NetBird answers without an activated MSP object, the feature hides itself.
- **Event ingestion is per tenant, and so is its fallback**: a tenant whose plan has no event streaming can instead opt into the **Traffic Events API pull** (Settings → Webhook while managing that tenant). Each account keeps its own opt-in flag, its own cursor and its own last-run status; the 5-minute scheduler walks main plus every tenant and skips the ones that left it off (which is the default). The pull uses that tenant's own API token, maps each flow into the webhook payload shape and stores it through the normal ingest path, so the tenant's Activity views, noise filters and retention behave identically to a streamed tenant. Enable it for a tenant **or** point NetBird's event streaming at the tenant's `/api/webhook/t/<id>` - not both.
- **DB isolation**: every tenant-relevant table carries a `tenant` column ('' = your main account) and it is part of the natural keys, so tenant data can never collide with - or surface under - another account. Device **notes/tags** already work per tenant; network grants, default profiles, the allow-duplicates flag, event filter rules and the blocklist are tenant-scoped too. Features not yet converted stay locked to the main account by the server-side allowlist.
- Tenant data is never cached together with main-account data (separate short-lived cache slots).
- Deleting a tenant here removes the MSP link/management - the customer's account data is not wiped by the app.
