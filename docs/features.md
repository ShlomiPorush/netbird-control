# Features in detail

The full feature reference. The [root README](../README.md) has the short overview; the per-feature
mechanics are in the other files of this folder (see [the index](README.md)).

## Activity & audit
- **Webhook receiver** - ingests NetBird [Generic HTTP Event Streaming](https://docs.netbird.io/manage/activity/event-streaming/generic-http) (traffic flows and management events).
- **Traffic Events API pull** (opt-in, per account) - for accounts whose plan has no event streaming: polls `GET /api/events/network-traffic` every 5 minutes and stores the flows exactly like streamed events, so every Activity view, filter and retention rule works on them unchanged. **Off by default** - enable it in Settings → Webhook, and leave it off wherever the streaming webhook is configured (two ingestion paths for the same flows). NetBird retains only ~48 hours of traffic events, so local history accumulates from the moment it is switched on; if the account's plan does not expose the endpoint the card says so and the app stops asking for an hour.
- **Audit Events API pull** (opt-in, per account) - the admin-event sibling of the traffic pull: for accounts whose plan has no event streaming it polls `GET /api/events/audit` every 5 minutes and feeds the admin/audit events through the same ingest path, so every Change Audit Log view, category filter and retention rule works on them unchanged. **Off by default** - enable it in Settings → Webhook, and leave it off wherever the Account Notifications / streaming webhook already delivers these events (two ingestion paths for the same events). The first run backfills existing history silently (no Telegram spam); genuinely-new events after that notify normally. If the account's plan does not expose the endpoint the card says so and the app stops asking for an hour.
- **Activity log** - search, filters (traffic type / protocol / user / date range), flow grouping, raw-JSON inspector, auto-refresh - plus a server-side **Summary view** (one row per source→destination conversation).
- **Change audit log** (Admin) - every change made through the app, alongside NetBird's own management events, with raw IDs resolved to names.
- **Outbound notifications log** (Admin → Notifications) - every email / Telegram message the app sends: recipient, sending feature, subject and sent/failed status, plus a full **Preview** of each message's rendered body (opened on demand and shown inside a sandboxed iframe - scripts, network and external images blocked).
- **IP history** (Admin → IP History) - who held each NetBird IP and when, searchable at a point in time (forensics).
- **Event filtering & purge** - rules drop known-noise traffic before storing; a gated purge tool (email allow-list) can delete already-stored matches. Per account: main and each managed tenant keep their own rules; from main, **Apply to All Tenants** replaces every tenant's rules with main's.

## Network management (delegated, via the NetBird API)
- Browse and manage **Networks**, **Peers** and **Users & Groups** with detail pages; create/rename/delete networks from the app.
- **Group management** (admins) - the group detail page is a full management surface matching the NetBird dashboard: the **Users** tab shows avatar + name/email, role, status, block state and last login with **Assign Users** and per-row/bulk **Remove**, and the **Peers** tab adds **Assign Peers** and **Remove** - user membership writes each user's `auto_groups` (PUT `/api/users/{id}`) while peer membership replaces the group's peer set (PUT `/api/groups/{id}`), routed through the MSP Provisioning Token when set and audited. The auto-managed **All** group stays read-only for membership. The other tabs are actionable too, scoped to the group: **Policies** has **Add Policy** (opens the same Access Control Policy editor as the Policies page, with this group prefilled as the source - you pick destinations, protocol and ports; saving creates a standalone policy), **Setup Keys** has **Add Setup Key** (Name, Reusable, Usage limit, Expires-in-days, Ephemeral, Allow-extra-DNS-labels - the key auto-assigns this group and its plaintext value is shown once with a copy button), and **Resources** has **Create Resource**, which routes to the Networks page since a resource always lives inside a network. The **Routes**, **Nameservers** and **Zones** tabs are read-only lists (the app has no NetBird routing / DNS management surface); their empty states note that a group is assigned when the route / nameserver / zone is created. Policies and setup keys are normal NetBird calls and work while managing an MSP tenant; all writes are audited.
- **Invite User** (admins) - invite someone by name + email with a role (User / Auditor / Network Admin / Admin) and auto-assigned groups, exactly like the NetBird dashboard: NetBird Cloud sends the invitation email, the user shows up as **Invited** right away, and a **Resend Invitation** action re-sends it (Users table row action and the user's detail page). NetBird Cloud refuses invitations issued by a service user (the email needs a real inviter identity), so the invite is sent as the **MSP Provisioning Token**'s real admin user when one is configured in Settings → NetBird API - without it the app tries the service token and, if NetBird rejects the inviter, says exactly which setting to fill in. The Auto-Assigned Groups picker prefills from the account's saved default and offers **Save Selection As Default** (stored per account, so each MSP tenant keeps its own). Works while managing an MSP tenant too, and is audited.
- **Delete User** (admins) - a row action in the Users table and a button on the user's detail page, with the official dashboard's warning that deleting a user also removes **their devices** and their dashboard access. The account owner, your own account and the app's own service user are never deletable. Deleting a main-account user also removes them from directly granted feature permissions, approval delegations and the Telegram approver mapping. Works while managing an MSP tenant (it deletes that tenant's user), and is audited by name/email.
- **Block / Unblock User** and **Reset MFA** (admins) - buttons on the user's detail page, worded like the official dashboard. Block stops the user signing in to NetBird, and until they are unblocked they hold no role, groups or permissions when signed in to this app (resending role + auto-assigned groups so they are never wiped); the owner, your own account and the app's own service user cannot be blocked. Reset MFA clears the user's MFA methods so they re-enroll on next login, and disables itself with a tooltip when the NetBird deployment does not serve MFA reset through the management API. Both work while managing an MSP tenant - user reads and writes are routed through the **MSP Provisioning Token**'s real admin user when configured, which is also what makes a managed tenant's **user list sync** (NetBird restricts the user list for service users, so without it tenant users showed as 0). Audited by name/email.
- **Add Peer** (Peers page) - the official NetBird install flow in a dialog, in two modes: **User Device** (Linux / Windows / macOS / iOS / Android, opening on the OS you're browsing from - install, then log in with your email account) and **Server** (Linux / Windows / macOS / Docker - install, then run with a setup key), with the exact per-OS commands, installer/store links and copy buttons. The server mode **generates the setup key inline** (one-off, single use, 24 hours, no auto-groups) and splices it into every tab's command; the key is shown once and never stored or logged (the audit entry keeps its name only). An empty account shows a **Get Started with NetBird** screen instead of the table. Works while managing an MSP tenant, and is audited.
- **Peers filters** - compliance (Non-Compliant / Bypassed), Inactive (offline 30/60/90+ days, with reviewed bulk-delete) and Tags. The search box also matches a peer's **MAC address** (`AA:BB`, `aa-bb`, `aabb` all work), and the peer detail page lists its **Network Interfaces** (IP + MAC) - both need NetBird v0.81+, which reports them.
- **Device tags & notes** (app-side metadata) - filterable, searchable, bulk-taggable, audited.
- **Resources** - create / edit / duplicate / enable-disable / delete, bulk delete, **Move To Network** and **Merge Into One** (both with rollback on failure), per-resource access policies, filters and pagination.
- **Address-conflict protection** - duplicate/overlapping addresses are blocked on create (per-network opt-out available), and when one user can reach the same exact address through two resources - including **cross-network** - a red banner names the resources and affected users with a one-click merge.
- **Troubleshoot page** (every user) - guided diagnostics: server-side device checks (connection, session, compliance, version, groups), **browser-side network checks** (management/signal reachability, real WebRTC STUN with automatic triage), and an **access-path analysis** for a chosen resource or a free-typed `IP:port` - is it routed through NetBird, do you have access, is that port open, does anything answer. Exit nodes are recognized, a plain-language verdict tells the user what to do (with a Request Access shortcut), NetBird's own "routing peer down" alerts show as a Known Issues banner, and a **Windows diagnostics script** is downloadable for the local checks a browser can't run.
- **Cleanup page** (Operations) - report-only hygiene sweep: orphaned/ineffective policies, unused groups, unreachable resources, stale devices. Nothing is deleted automatically, and deliberate findings can be marked **Ignored** (audited, excluded from the weekly digest).

## Access control
- **One policy editor everywhere** - the same Access Control Policy modal serves the Policies page and every resource's Access Control tab, with **copy/paste** of port lists and whole policies. **Duplicate** (Policies row menu) opens the create dialog prefilled from a policy and saves nothing until **Add Policy**; a policy whose rules the single-rule editor can't reproduce exactly (several rules, a disabled or Drop rule, an SSH rule, a source resource) is duplicated with its rules copied verbatim, and such policies are edited name / description / status / posture only (their rule fields are shown read-only, and the server refuses a rebuild that would change them), so a save never changes their rules.
- **Access Profiles** - reusable definitions: Shared (one policy many resources inherit) and Direct (protocol/ports preset), plus per-network default profiles.
- **Policy name templates + Tidy Names** - admin-configurable naming templates (separate tier for multi-policy "shared" resources), and a preview-based bulk rename that touches names only.
- **Posture Checks** editor (client/OS version, geo, network range, running process, and **Certificate** - NetBird v0.81+), attachable to Shared profiles. The Certificate check takes one or more root / intermediate CA certificates (PEM); each is parsed on the server and shown with its subject and **SHA-256 fingerprint** (and flagged when expired or not a CA). iOS and Android clients always fail it. Check types the editor doesn't know are kept as they are on save.
- **Network Access grants** - which Entra groups may edit each network, with policy-source membership split from edit rights - plus admin-curated **grantable source groups**: a short list editors may pick as policy sources, without ever seeing the full group directory.
- **Address blocklist** - IPs/CIDRs/domains that may not become resources (also enforced on automation imports), per-network scoping, per-entry pause (Disable), and an explicit scan → review → confirm enforcement on existing resources. Entries can also be **Limit** rules: inside a protected range only CIDRs up to a chosen width are allowed (e.g. `10.0.0.0/8` max `/24` - an editor can't add the whole internal network as one resource, while hosts inside stay addable). Admins may knowingly override a block (warned inline, audited); everyone else is always blocked. Per account: main and each managed tenant keep their own list; from main, **Apply to All Tenants** replaces every tenant's list with main's (network-scoped entries are skipped).
- **Temporary Access** - time-boxed grants to a resource / network / group / profile, applied immediately and fully torn down on expiry. **Least-privilege**: the grant mirrors each target's existing protocol/port exposure. Live countdown, revoke and extend built in.
- **Access Requests** - self-service requests (per-port policy entries are individually requestable) approved **in-app or straight from Telegram** (duration submenu, typed deny reason, target editing). Approvers are designated by an Entra group - no admin rights needed.
- **Device bypass requests** - compliance-blocked devices can request an EDR bypass: timed or unlimited, extendable, removable, and a **Temporary Device** flag that deletes the device when the period ends. Owners are emailed automatically when their device is blocked on login.
- **Automatic EDR bypass by OS** (Settings → Security, **off by default**, per account) - devices that can never run the EDR agent (phones, Linux servers) are bypassed automatically per platform (iOS/iPadOS, Android, Linux, Windows, macOS), timed (1-365 days) or unlimited, using the exact same mechanism and bookkeeping as a manual bypass - so expiry, badges and recertification are unchanged (unlimited ones enter every review round). Capped at 25 devices per sync, audited (`peer.bypass_auto`) and alerted on Telegram. **Explicitly revoking** an auto bypass excludes that device permanently; a timed one that merely expired renews. The OS is self-reported and can be spoofed - see [Permissions & Security](permissions-and-security.md#automatic-edr-bypass-by-os).
- **Recurring access** - weekday/time-window schedules that create and revoke grants automatically.
- **Auto-approval** - trusted Entra groups and per-resource self-service rules (optionally pinning exact ports); mixed requests split between instant grant and human review.
- **Request escalation** - one Telegram reminder for stale requests + auto-expiry (tunable).

## Automation (auto-provision resources)
- Auto-create NetBird resources from an **external HTTP source** (JSON with field mapping, or IP-per-line text), on a schedule or on demand.
- Full lifecycle (create / adopt existing / disable / delete), a safety floor against broken responses, per-run logs and repair tools.
- **Dry run** - a zero-write report of exactly what a sync would do, with per-item verdicts and CSV export.

## Notifications (Telegram & Email)
- **Telegram** - app audit events and a selectable set of NetBird events, routed to per-category forum topics (auto-created), with IDs resolved to names and humanized formatting. Sends go through an internal queue that pauses and retries on rate limits (429), so bursts are never dropped. **Per account:** main and each managed tenant have their own bot/chat/topics (Settings → Telegram in tenant mode; tenant tokens are settings-only, never env). A tenant's audit + access-review alerts additionally **mirror to main's** channel - tagged with the tenant name - under main's **Tenant Activity** toggle (default on); a tenant's NetBird-event and anomaly alerts stay on the tenant's own Telegram only.
- **Email (SMTP)** - requesters and grantees are notified on approve / deny / grant / expiry; env- or app-managed config with a send-test button.
- **Anomaly alerts** - device country switch, new-country enrollment, off-hours admin actions, per-device traffic spikes (thresholds in Settings → Security).
- **Background job alerts** - Telegram 🚨 when a scheduled job fails 3 times in a row, ✅ on recovery (transition-only, never per run).
- **NetBird account notifications** - NetBird's own notification webhook (routing peer down/deleted, IdP/EDR sync expiry, pending approvals) ingests into the app with its own Bearer token: forwarded to Telegram, shown as a self-clearing **Known Issues** banner on Troubleshoot and in the dashboard's Needs Attention. A **one-click setup** (Settings → Webhook) auto-creates/updates the NetBird webhook channel for the current account (main or a managed tenant) with all event types - it mints and stores a fresh ingest token and points the channel at the account's receiver URL.
- **Weekly review digest** - everything currently open (grants, bypasses, auto-approval, permissions, pending) plus **This Week** (new devices, request outcomes, billed-users change) and **Hygiene** (Cleanup counters, conflicts). Telegram + optional email, scheduled or sent on demand with **Send Now**.
- **Approval delegation** - time-boxed approval rights to cover an approver's absence; expires by itself.
- **Access recertification** - periodic keep/revoke rounds over all standing access, with full decision context inline, due dates, audits and a Past Reviews history.

## Interface
- **Dashboard** - fleet tiles (incl. NetBird's billed-users count), a **Needs Attention** feed (approvals, expiring grants, non-compliant devices, conflicts, failed automations, NetBird alerts), a 24h traffic chart and recent changes; restricted users get a personal home.
- **Reverse Proxy page** (NetBird Cloud) - services + **ingested access logs** (kept per your Data Retention), full service management: create, an **Expose Docker Container** wizard with rollback, and editing of targets (peer / resource / cluster / **Docker container by DNS name** - its domain resource is created or reused automatically) / authentication / access control / advanced settings. Each HTTP target has a per-path **Access** setting (NetBird v0.81+): Use Service Authentication, **Bypass Authentication** or **Block Access** - overrides are badged in the editor, the Targets sub-table and the service row, a bypass names the path that opens without login and is confirmed on save, and NetBird's rules are checked first (HTTP services only; a NetBird-Only service allows Block but not Bypass). Every proxy in the cluster must run v0.81+ to enforce it. Target fields the app doesn't edit are kept on save. Access logs show a **CrowdSec** badge (Ban / Captcha / Throttle / Unavailable, with **Observe** when only logged). A **Clusters & Domains** tab shows the proxy clusters and domain bases with on-demand sync from NetBird. Gated by its own permission.
- **MSP Tenants** (NetBird Cloud MSP accounts; auto-hidden otherwise) - create/manage customer tenants like the official MSP portal (TXT domain verification, permission groups, usage counts, and a per-tenant **Readiness** checklist - domain verified, service user, events webhook, notifications webhook, Telegram - shown as an `N/5` chip), and **Manage** switches the whole app onto the customer's account - a tenant behaves exactly like the main account: same pages, same synced-to-DB pipeline (peers/users mirrors, event ingestion via the tenant's own webhook + retention, plus the tenant's own **Telegram** notifications - all configured in **Settings → NetBird Settings / Webhook / Telegram / Data Retention** while managing it, with an endpoint URL that carries the tenant id, proxy logs, history) and the same app features (temporary access, recurring access, recertification, automations, event filtering, blocklist, system health - background jobs run per account), all rows tenant-scoped so nothing from one tenant can surface in another. New tenants are **seeded from a Tenant Defaults profile** on creation (filter rules, blocklist, retention, and the **full official NetBird account settings set** - peer/user approval, multi-factor authentication (cloud MFA, via the per-account MFA service) with remember-browser, peer session + reconnect expiration, groups propagation, JWT group sync, restrict regular users, routing-peer DNS, traffic events + kernel traffic reporting, automatic updates, peer expose, lazy connections, and optionally DNS domain / network ranges; only account-specific group-based settings are excluded). This profile is an **explicit admin-defined reference** (Settings → Tenant Defaults, MSP only), not a live copy of main - so what suits your own account never leaks onto customers by accident (the infra fields are applied only when you explicitly set them); if no profile is saved it falls back to copying main's live config (unchanged legacy behavior), and each nb toggle / retention / copy-flag is curated per field. The **Add Tenant** dialog exposes these as an optional **Initial Setup** checklist - sync settings from defaults, create the managed service user, and configure NetBird account notifications (all on by default) plus configure activity events (off; needs a NetBird Business plan) - so any step can be skipped and re-run later. From main, **Apply to All Tenants** pushes the event-filter rules or blocklist to every tenant at once, and each tenant has a per-tenant **Apply Defaults** + **Settings Sync drift** view (replace semantics) that lists exactly which setting differs from the profile. Editing an active tenant also offers a **Plan** tab replicating the official plan cards - Team and Business with their description, price per user / month in your MSP account's billing currency, limits and feature list - where an **Upgrade** subscribes that tenant to the plan; it is a **real billing change** charged to your MSP account, so it is behind an explicit confirmation and audited (`tenant.plan`), free/trial tenants going through NetBird's initial-subscription call and paying ones through the update call. Tenant credentials are **self-managed**: the app provisions a service user + token inside each tenant and rotates it automatically. A **Fleet Report** tab gives a one-screen management snapshot of every tenant (plan, users active/total, billed users, peers total/online/offline-30d, outdated clients vs latest, known issues, webhook/Telegram/service-user status, last event) with a manual refresh - the plan/users/billed/known-issues figures are read per tenant in its own context, and known issues equals exactly what that tenant's Known Issues banner shows. An optional **Weekly Digest** (Fleet Report → Digest) summarizes every tenant plus fleet totals to main's Telegram and/or emails on a chosen day/hour - **disabled by default** with a **Send Now** action. Main's Telegram also has a **Tenant Activity** toggle to mirror managed tenants' audit + scheduler alerts into main's group, tagged per tenant. See [docs/msp-tenants.md](msp-tenants.md).
- **Access Management hub** - Requests, Temporary Access and Access Review as one Settings-style page, sections filtered per viewer. An **Operations hub** groups everything an admin *manages* (as opposed to app configuration): System Health, Automation, Access Profiles, Posture Checks, Network Access, Blocklist, Event Filtering and Cleanup - leaving **Settings** to pure configuration (connections, notifications, permissions, retention, backup).
- **⌘K command palette** over everything the viewer may see; consistent sortable/paginated tables; full mobile layouts; route-level code splitting; accessible, keyboard-navigable dialogs and menus.
- **Log loading experience** - the log pages (Traffic Events, Admin → Audit Log / Admin Events / IP History / Outbound Messages, Reverse Proxy access logs) show a branded animated network panel with a progress percentage instead of a plain spinner, plus a slim progress bar at the top of the window while a heavy log query runs. The percentage is an estimate (a browser cannot measure query progress), and both are light/dark aware and honor **reduced motion**.

## Auth & permissions
- **Optional SSO** via Azure AD / Entra ID (OIDC): admins (NetBird owner/admin role or an AD admin group) see everything; everyone else only their own data and granted networks.
- **Feature permissions** for non-admin users/groups: View All Activity · View All Peers · View Audit Logs · Manage Temporary Access · Manage All Networks · Manage Reverse Proxy · Troubleshoot All Peers · Tenant Support. Enforced server-side, audited. See [docs/permissions-and-security.md](permissions-and-security.md).
- **Tenant Support** permission (Settings - Permissions): lets a non-admin switch into MSP tenants and manage each one exactly like an admin *inside* that tenant - with **no** admin rights on the main account and no tenant creation or deletion. The Troubleshoot page is available per tenant, so support desk staff can diagnose a customer's devices while managing that tenant.
- **Short sessions by design** - rolling idle timeout + absolute caps (stricter for admins), all tunable.
- **Hardening** - CSP + security headers, constant-time webhook token compare with per-IP throttling of failures, write-only secrets, and a **read-only NetBird mode** (`NETBIRD_READONLY=true`) for instances that must not change the tenant.
- **System Health** (Operations) - live status of every background job, DB sizes, NetBird API connectivity and open-exposure counters. Available per tenant: the account-scoped numbers (row counts, grants, bypasses, retention, NetBird health via the tenant's own token) reflect the managed account; total DB size and infra fields stay global.
- **Data Retention** (Settings) - optional daily purge of stored events/logs older than N days (default: keep forever); app audit and IP history are never purged. Per account: main and each managed tenant set (and purge to) their own window independently.
- **NetBird Settings** (Settings, admin) - a **live editor for the current account's own NetBird settings** (Authentication, Groups, Permissions, Networks, Clients - the full official settings set). It edits the account's **actual** settings, not a template, and works for **main and for a managed tenant** (in tenant mode it edits that tenant's account). One **Save** merges the change onto the account's live settings and writes it back. The infra fields (DNS domain / network ranges) are editable but warn that changing them **re-allocates every peer IP**, and are sent only when actually changed; cloud MFA is applied via the per-account MFA service when the API base serves it. **Reject Hostname Collisions** (Clients, NetBird v0.81+) is shown only when the account's NetBird exposes it; in **Tenant Defaults** it is **Keep Tenant Setting** / On / Off, existing profiles leave it unmanaged, and a tenant on an older NetBird is skipped (its drift row reads Not Supported). Distinct from **Tenant Defaults**, which is the seed template for *new* tenants. Blocked by `NETBIRD_READONLY`.

## Configuration
- Almost everything is **DB-backed and editable in-app** (Settings) without a redeploy: app name, time zone, NetBird API connection, webhook tokens, Telegram, SMTP, security limits, filtering rules and more.
- **Backup & Restore** - two tiers. **Tier 1, the settings export** - export/import the whole configuration as JSON, applied without a restart. Includes the app-configuration tables across all tenants (Event Filtering, Blocklist, Automations, Recurring Access, Access Profiles + per-network defaults, Network Grants, Templates, Cleanup Ignores); restoring **replaces** those sections. **Secrets are never included** (API/webhook/Telegram tokens, SMTP password, automation source credentials) and state/history (events, audit, grants, run history) is never exported - so this file is **safe to share**. **Tier 2, the internal encrypted backup** - a **complete** backup (all config **plus every secret**) written to a mounted folder (`BACKUP_DIR`) on a daily schedule and **envelope-encrypted**: a public key on the server encrypts each backup, but only the **admin passphrase** (set in the UI, never in env) can decrypt it - **the server itself cannot open its own backups**. A forgotten passphrase means the backups are unreadable, by design. Disabled until a passphrase and folder are configured.

## Connecting NetBird events

Then point NetBird at it. The fastest way is the **one-click setup** at **Settings → Webhook** (admin-only): a **Configure In NetBird Automatically** button on **both** the Activity Events and the Account Notifications cards creates or updates the matching NetBird integration in the current account for you - it wires up the Generic HTTP Event Streaming integration (activity + traffic) and the Account Notifications webhook channel, handling the ingest token automatically. The events token is regenerated unless it is env-managed (`WEBHOOK_AUTH_TOKEN`), in which case it is reused. When managing an MSP tenant, each button configures that tenant's own NetBird account against its `/t/<tenant-id>` endpoint.

Each card also shows a **live status pill** so you can tell at a glance whether the feature is actually set up: the app reads NetBird's own integration state for the current account and shows green **Active** when the matching integration exists and is enabled (hover for when the last event/notification arrived), amber **Disabled In NetBird** when the integration exists but is turned off, gray **Not Configured** when there is no matching integration, and **Unknown** when the state cannot be read (for example a plan without event streaming). This deliberately does not infer status from arriving data - traffic events can also arrive via the API Pull below, so their presence is not proof the streaming integration exists. The Traffic Events API Pull and Audit Events API Pull cards each show a matching **On** / **Off** pill for their own opt-in flag.

Or point NetBird at it manually: in the NetBird dashboard go to **Integrations → Event Streaming → Generic HTTP** and set:
- **Endpoint URL:** `https://your-server:3000/api/webhook`
- **Authentication:** Bearer Token - matching the webhook token. Set it in your `.env` (`WEBHOOK_AUTH_TOKEN`) **or** in-app at **Settings → Webhook** (admin-only; copy the endpoint URL from there too). When managing an MSP tenant, that page shows the tenant's own token and a `/api/webhook/t/<tenant-id>` endpoint so the tenant's NetBird ingests into its own account.

## Architecture

| Layer | Technology |
|---|---|
| Frontend | React 18 + Vite + TypeScript + React Router + TanStack Query + Tailwind CSS + lucide-react |
| Backend | Node.js + Express |
| Database | PostgreSQL 17 |
| Auth | `express-openid-connect` (OIDC) + Microsoft Graph (AD group membership) |
| Packaging | Docker (multi-stage) + Docker Compose; images on GHCR |

The production backend serves the prebuilt single-page app from a single origin (default port `3000`).

**Log-table performance** - every log read is scoped `WHERE tenant = ...` first, so the big log tables (events, admin events, proxy access logs, app audit) are indexed on `(tenant, timestamp DESC)`. Those indexes are built **after** the server starts listening and `CONCURRENTLY` (online, no boot delay and no write lock) - on a multi-GB events table the first boot after upgrading logs `[Index] building ...` for a few minutes while the app serves traffic normally, and an interrupted build is detected and rebuilt on the next start. Paginated log lists count up to **50,000** matches and then show `50,000+` instead of an exact total, so a page load never pays for a full count - narrow the filters or the date range for a precise number.

## Key endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/docs` | **Interactive API reference (Swagger UI)** - every endpoint, grouped by area, with “Try it out” |
| `GET` | `/api/docs/openapi.json` | The raw OpenAPI 3 spec (for Postman / codegen) |
| `POST` | `/api/webhook` (or `/api/webhook/t/:tenantId`) | Receive a NetBird event; the optional `/t/<id>` path routes it into a managed tenant's account (per-account bearer-auth) |
| `GET`/`PUT` | `/api/traffic-pull` | 🔒 The current account's Traffic Events API pull - opt-in flag plus last-run status |
| `GET`/`PUT` | `/api/audit-pull` | 🔒 The current account's Audit Events API pull - opt-in flag plus last-run status |
| `GET`/`PUT` | `/api/edr-auto-bypass` | 🔒 The current account's automatic EDR bypass rules (per OS; off by default) |
| `GET` | `/api/health` | Health check |
| `GET` | `/version.txt` | Current app version (plain text) |

The full HTTP API (logs, peers, networks, policies, groups, access profiles, posture checks, automations, blocklist, audit, settings…) is documented interactively at **`/api/docs`** - the spec is introspected from the live router, so it never drifts from the code. Endpoints requiring admin are marked 🔒. The docs sit behind login when SSO is enabled, and “Try it out” reuses your session.
